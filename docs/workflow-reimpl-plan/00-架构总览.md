## 1. 背景与目标

### 1.1 为什么重实现

原 `backend/app/workflow_v2` 验证了核心思想的可行性与生产价值：

> **声明式 YAML → LangGraph 状态图编译器 + 进程级注册运行时。**

但在工程层面，原代码把"通用引擎能力"与"AIOps 故障分析领域逻辑"揉在了一起，已经不适合继续演进：

| 问题类别 | 现状（原 workflow_v2） | 后果 |
|---|---|---|
| 职责混杂 | `graph_builder.py` 单文件约 815 行，同时承载状态模型合成、图构建、注册运行时三种职责 | 任何一处改动都牵连全局，无法独立测试 |
| 领域耦合 | `NodeType` 携带 19 种领域枚举（plan/worker/extract/dispatcher…）；`create_state_model` 硬编码 `circle_conclusions`/`planner_result` 等业务字段名特判（原 graph_builder.py:263-275） | 引擎不再通用，新业务只能改引擎源码 |
| 并发隐患 | `WorkflowRegistry` 是进程级单例，被 Web 线程池共享，`execute_workflow` 非原子，且在**共享节点实例**上就地 `clear_execution_history()`（原 graph_builder.py:637-639） | 两个并发请求打同一 workflow_id 会互相清空/覆盖执行历史（H1） |
| 安全隐患 | YAML 硬编码 API key；Neo4j 默认密码 `dms123!!`（原 utils.py:230）；路由闭包 `print` 完整 state 到 stdout（原 graph_builder.py:489） | 密钥泄漏、日志污染（H6） |
| 死代码/死异常 | 死 `try/except`（`except` 分支逻辑不可靠且从未被测试覆盖）+ 降级路径无配置开关、硬编码 mock 返回；模块级无界 `_subgraph_cache` | 失败路径不可预测（H2/H4） |

因此本项目**不是从零设计，而是"抽取 + 提纯"**：把原代码中生产级、被验证过的设计（见第 3.1 节 K1..K10）原样沿用，把领域逻辑丢弃（见第 3.2 节），把逻辑混乱处修正（见第 3.3 节 C1..C9），把已识别隐患在重实现中根除（见第 10 章 H1..H7）。

### 1.2 本期范围

**目标**：在新项目中重新实现一个**精简、生产级**的声明式工作流引擎。

**本期只实现 2 个具体节点类型**（外加抽象基类）：

| 节点 | 定位 | 代表能力 |
|---|---|---|
| `BaseNode`（抽象） | 所有节点的统一契约 | `build_runnable()` / `validate_config()` / 执行日志累积 |
| `LLMNode` | 大模型调用节点 | 多供应商（openai/anthropic）、env 密钥、懒加载、429 指数退避 |
| `HTTPNode` | 通用 HTTP 调用节点 | URL/headers/body 模板渲染、`response_path` 结果提取、显式可配置 retry/mock |

**非目标（本期明确不做，见 3.2）**：其余 17 种领域节点、子图嵌套、`Send` 并行扇出、Neo4j 计划生成、MCP client、game_agent/node4j 等一切领域资产。

### 1.3 顶层验收标准

1. 示例 YAML `condition_branch.yaml`（即"LLM → 条件边 → HTTP"的组合示例）能端到端跑通，返回规范响应信封。
2. 同一 `workflow_id` 多线程并发执行，运行日志完整且互不串扰（H1 验证）。
3. 全量测试覆盖率 ≥ 80%，失败路径（LLM/HTTP 抛错）有显式单测覆盖，并统一抛出《01-分阶段开发计划.md · 分阶段开发计划》"异常契约"小节定义的异常族（H2 验证）。
4. `grep` 全仓无硬编码密钥；日志脱敏单测通过（H6 验证）。
5. 任何模块 < 400 行、任何函数 < 50 行（R8）。

## 2. 设计原则

| # | 原则 | 具体要求（可检查） |
|---|---|---|
| P1 | **声明式** | 工作流 = 数据（YAML 五元组 K1），不是代码。新增一个工作流不需要写 Python；节点行为差异全部收敛到 `config` 字典。 |
| P2 | **通用引擎** | 引擎内禁止出现任何业务字段名。reducer 只能来自 YAML 显式声明（R2）；`NodeType` 精简到本期需要的集合（C8）；节点类型通过注册表扩展（R4）。 |
| P3 | **不可变状态** | 节点 `func(state) -> dict`，只返回**状态更新增量**，绝不 mutate 传入的 state（R3）。state 的最终合并由 LangGraph channel reducer 负责。 |
| P4 | **可测试** | 严格 TDD（R7）：RED → GREEN → REFACTOR。每个模块镜像测试；LLM/HTTP 一律 mock 边界依赖；失败路径与成功路径同等覆盖。 |
| P5 | **生产级** | 密钥一律 env（R5）；结构化日志 + 脱敏（C9/H6）；线程安全（H1）；无死 try/except（R6）；无无界缓存（R10）；错误在边界处显式校验并快速失败（R9）。 |

五条原则冲突时的优先级：**正确性与安全性（P5/P3） > 通用性（P2） > 可测试性（P4） > 声明式便利（P1）**。

### 3.1 保留清单（K1..K10）——生产级设计，原样沿用

| 编号 | 主题 | 原代码怎么做（佐证） | 新实现怎么做 | 为什么保留 |
|---|---|---|---|---|
| **K1** | 声明式 YAML DSL 五元组 | `models.py:221-229` `WorkflowDefinition`：`workflow_id` / `nodes` / `edges` / `entry_point` / `state_schema`（另含 `operator_logs` / `execution_history`） | `workflow_engine/models.py` 保持五元组为必填核心字段；`description` 允许保留但非模型字段 | 这是整个引擎的输入契约，已被生产验证；改 DSL = 改所有 YAML，代价极高 |
| **K2** | 动态 Pydantic 状态模型 | `graph_builder.py:289-302`：`create_model` + 基类 `ConfigDict(extra="allow")` | `state.py` 的 `StateModelFactory.create_state_model(state_schema)` 产出继承 `extra="allow"` 基类的动态模型 | Dify 风格：允许节点写入未声明字段，DSL 作者不必预声明全部中间字段（ADR-001） |
| **K3** | reducer 机制 | `graph_builder.py:245-262`：`reducer="add"` → `Annotated[list, operator.add]`；`reducer="last"` → `Annotated[T, _last]`，`def _last(a, b): return b` | `state.py` 原样保留两种 reducer 语义与 `_last` 定义；未声明 reducer → LangGraph 默认 LastValue（后写覆盖） | 这是 LangGraph channel 合并语义的标准接入方式，多节点写同一字段时不丢数据 |
| **K4** | BaseNode 契约 | `node/base.py`：抽象 `build_runnable()` / `validate_config()`；`log_execution` / `get_execution_history` / `clear_execution_history`；具体节点返回 `RunnableLambda(func).with_config(tags=[name])`（`node/llm_node.py:148`、`node/http.py:121`） | `nodes/base.py` 保持同一契约：唯一执行单元是 `build_runnable() -> RunnableLambda(func).with_config(tags=[name])`，`func(state) -> dict` | 统一契约是"节点可插拔 + 图可编译 + 日志可追踪"三者的共同地基 |
| **K5** | 插件式节点工厂 | `node/factory.py`：`_custom_node_registry` + `register_node_type(name, cls)` + `create_node(definition, operator_log=None)`，先查注册表再内置分发 | `nodes/factory.py` 保留同名 API；内置 llm/http 以最小分发兜底，领域分支一律走注册（R4） | 扩展节点类型不改引擎源码；错误信息能列出已注册类型，便于排障 |
| **K6** | build_graph 七步 | `graph_builder.py:137-181`：`_validate_definition` → 创建状态模型 → `StateGraph(state)` → `_add_nodes` → `_add_edges` → `set_entry_point` → `compile()` | `graph_builder.py` 的 `GraphBuilder.build_graph` 严格保持七步顺序（方法名规范为 `_validate_definition`/`_add_nodes`/`_add_edges`） | 顺序即正确性：先校验后构图、先节点后边、最后 compile；七步也是 Phase 6 的测试骨架 |
| **K7** | 条件边路由器 | `graph_builder.py:461-512`：把 `EdgeDefinition.condition`（点路径，支持 `"a.b == 'x'"` 等值比较与纯路径真值判断）编译成 `router(state) -> str` 闭包，经 `graph.add_conditional_edges` 接入 | 保留同一 DSL 表达力与闭包方案；**但**调试输出改 logging、no-match 行为显式可配置（C3） | 条件路由是工作流表达力的核心；闭包方案零运行时依赖，无需引入表达式引擎 |
| **K8** | WorkflowRegistry 接口面 | `graph_builder.py:526-814`：`register_workflow` / `get_workflow` / `has_workflow` / `list_workflows` / `execute_workflow` + 查询接口（operator_logs、execution_history、按节点查询） | `registry.py` 保留全部公开接口名与语义（`execute_workflow` 返回 `RunResult`，未知 `workflow_id` 抛 `WorkflowNotFoundError`）；内部实现重构为线程安全（H1）+ 运行级日志收集（H3） | 接口面已被上层调用方使用；只重构实现、不改契约，降低集成风险 |
| **K9** | utils 两个状态工具 | `utils.py:144-179`：`convert_state_to_dict`（pydantic→`model_dump` / dict 直通 / 其它→`{}`）；`map_output_to_state`（Dify 双写：`{node_name}_result` 整包 + 逐字段平铺） | `utils.py` 仅保留这两个函数（C7）；双写语义保留且文档化，增加可配置开关 `dual_write`（默认开，C4） | 一进一出是节点契约（R3）的落地点；双写让下游既可按节点名取整包、也可按字段名直取 |
| **K10** | LLM 多供应商 / HTTP 模板化 | `node/llm_node.py:49-82`：按 `llm_type` 选 `ChatOpenAI`/`ChatAnthropic`，懒加载实例；`node/http.py`：`url`/`method`/`headers`/`body_template` 占位符渲染 + `response_path` 结果提取 | `nodes/llm_node.py`（+`LLMConfig`）与 `nodes/http_node.py`（+`HTTPNodeConfig`）沿用同一设计；密钥改 env、失败路径显式化（H2/H6） | 这两个节点的全部"通用能力"都在这里，丢弃领域字段（如 `worker_result`/`short_memory` 硬编码输出）后即生产可用 |

## 4. 目标项目结构

### 4.1 目录树

> 包名 `workflow_engine` 为占位符，落地时可整体改名（改名仅需替换导入路径，不影响任何契约）。

```
workflow_engine/
├── __init__.py              # 包入口：版本号 + 顶层 API 再导出（WorkflowRegistry、register_node_type 等）
```

### 4.2 模块职责（一句话 + 关键对外 API）

| 模块 | 一句话职责 | 关键对外 API |
|---|---|---|
| `models.py` | DSL 的全部 pydantic v2 模型与精简 `NodeType`，是引擎的**输入契约层** | `WorkflowDefinition` / `NodeDefinition` / `EdgeDefinition` / `StateFieldSchema` / `OperatorLog` / `ExecutionLog` / `NodeType` |
| `state.py` | 把 `state_schema` 合成带 reducer 的动态状态模型 | `StateModelFactory.create_state_model(state_schema) -> type[BaseModel]` |
| `graph_builder.py` | 把 `WorkflowDefinition` 编译成 LangGraph 可执行图（七步） | `GraphBuilder.build_graph(definition) -> CompiledGraph` |
| `registry.py` | 进程级工作流注册运行时：注册/查询/执行/删除 + YAML 目录加载 | `WorkflowRegistry.register_workflow/get_workflow/has_workflow/list_workflows/execute_workflow/delete_workflow/查询接口`；`load_definitions_from_dir(path)`；`execute_workflow -> RunResult` |
| `utils.py` | 节点与状态之间的双向转换（进/出契约的落地点） | `convert_state_to_dict(state) -> dict`；`map_output_to_state(node_name, output, state=None, ...) -> dict` |
| `logging_conf.py` | 结构化日志初始化与敏感数据脱敏 | `setup_logging(level="INFO", *, json_output=False)`；`RedactFilter` 脱敏过滤器 |
| `nodes/base.py` | 节点统一契约与执行日志累积 | `BaseNode`（抽象） |
| `nodes/factory.py` | 插件注册表 + 节点创建分发 | `register_node_type(name, cls)`；`create_node(definition, operator_log=None)` |
| `nodes/llm_node.py` | 大模型调用节点 | `LLMNode` / `LLMConfig` |
| `nodes/http_node.py` | 通用 HTTP 调用节点 | `HTTPNode` / `HTTPNodeConfig` |

### 4.3 模块依赖方向

**分层单向依赖，只允许向下，严禁反向与跨层回调：**

```
L4  registry.py
      │ 依赖
      ▼
L3  graph_builder.py ────────► state.py
      │ 依赖                      │ 依赖
      ▼                           ▼
L2  nodes/factory.py          models.py ◄────────────┐
      │ 依赖                                          │ 依赖
      ▼                                               │
L1  nodes/llm_node.py  nodes/http_node.py             │
      │ 依赖              │ 依赖                      │
      ▼                   ▼                           │
L0  nodes/base.py ──► utils.py ───────────────────────┘
        │ 依赖
        ▼
    models.py

横切：logging_conf.py 不依赖任何业务模块，任何模块都可 import 它
```

**依赖红线（违反即架构腐化）：**

- `models.py` 不得 import 任何引擎模块（只依赖 pydantic/标准库）。
- `nodes/*` 不得 import `registry` / `graph_builder`（节点不知道图与注册表的存在）——这同时根除 H5 构建期快照反模式。
- `utils.py` 不得 import LLM/HTTP 客户端库（C7）。
- 需要引用其它工作流时，必须在**运行期惰性解析**（通过传入的回调/registry 句柄），禁止构建期拷贝快照（H5）。

## 5. 核心数据流全景

### 5.1 两个阶段

引擎运行分为**构建期（注册时）**与**运行期（执行时）**，二者严格分离：

- **构建期**：YAML → 模型校验 → 状态模型合成 → 图编译。产物是 `CompiledGraph`，可被重复执行。
- **运行期**：`invoke(input_data)` → 节点逐个执行 → reducer 合并状态增量 → 包装返回 `RunResult`（最终输出 + 运行级执行日志，见术语表）。

### 5.2 总体流程图

```
 ┌─────────────────────────────────────────────────────────────────────┐
 │                          构建期（注册时一次）                          │
 └─────────────────────────────────────────────────────────────────────┘

   YAML 文件 (config/examples/*.yaml)
      │
      │  registry.load_definitions_from_dir() / yaml.safe_load
      ▼
   dict ──► WorkflowDefinition(**data)          ◄── pydantic 边界校验（R9）
      │         models.py：五元组 K1
      │
      │  registry.register_workflow(definition)
      ▼
   GraphBuilder.build_graph(definition)          ◄── 七步 K6
      │
      │  ① _validate_definition                  （C5：干净完整校验）
      │  ② StateModelFactory.create_state_model  ◀━━━━━━━━━━━━━━━━━━━┓
      │        state.py：reducer 仅由 YAML 显式声明驱动（C2）        ┃
      │        ★ state 自动生成发生在这一步 ★                        ┃
      │  ③ StateGraph(state_model)                                 ┃
      │  ④ _add_nodes：create_node → build_runnable（K4/K5）        ┃
      │  ⑤ _add_edges：普通边 + 条件 router 闭包（K7/C3）           ┃
      │  ⑥ set_entry_point                                          ┃
      │  ⑦ compile()                                                ┃
      ▼                                                             ┃
   CompiledGraph  +  nodes_map{node_name: BaseNode}                 ┃
      │                                                             ┃
      │  存入 Registry 三张映射（同增同删，C6/H7）                    ┃
      ▼                                                             ┃
   _registry / _definitions / _nodes_map                            ┃
                                                                    ┃
 ┌─────────────────────────────────────────────────────────────────┐ ┃
 │                        运行期（每次请求）                          │ ┃
 └─────────────────────────────────────────────────────────────────┘ ┃
                                                                     ┃
   registry.execute_workflow(workflow_id, input_data)                ┃
      │                                                              ┃
      │  ① 取该 workflow_id 的 threading.RLock 串行化（H1）           ┃
      │  ② 创建 run-scoped RunLogCollector 并 set 进 ContextVar（H3/ADR-004）   ┃
      │  ③ compiled_graph.invoke(input_data)                         ┃
      │       │                                                      ┃
      │       │  LangGraph 按拓扑执行每个节点：                        ┃
      │       │    state ──► convert_state_to_dict ──► func(state)   ┃
      │       │                          R3：func 只读不 mutate ━━━━━┛
      │       │    func 返回 dict 增量 ──► map_output_to_state（K9/C4）
      │       │                          双写 {node}_result + 逐字段
      │       │    增量 ──► channel reducer 合并（add / last / LastValue）
      │       │    条件节点：router(state) -> str 选择出边（K7/C3）
      │       ▼
      │  ④ collect() 收集本次运行全部 ExecutionLog（覆盖所有被执行节点，H3）
      │  ⑤ 释放锁
      ▼
   RunResult（workflow_id / run_id / output / execution_logs /
              started_at / finished_at / duration_ms）
      │
      ▼
   入口层（Phase 8）包装为规范响应信封
   { "success": true, "data": {...}, "error": null, "metadata": {...} }
```

### 5.3 节点内部状态流（R3 契约的放大图）

每个节点的 `func` 必须严格走这条管线，不得旁路：

```
LangGraph 传入 state（动态 Pydantic 实例）
        │
        ▼
convert_state_to_dict(state)          # 进：pydantic→model_dump / dict 直通 / 其它→{}
        │
        ▼  state_dict（只读使用，禁止 mutate）
节点业务逻辑（LLM 调用 / HTTP 请求 / …）
        │
        ▼  node_output: dict（节点原始产出）
map_output_to_state(node_name, node_output, state_dict)   # 出：Dify 双写
        │
        ▼  state_update: dict
        │   ├─ "{node_name}_result": node_output   （整包，双写开关可关）
        │   ├─ 逐字段平铺 node_output 各键           （双写开关可关）
        │   └─ "history": 结构化追加条目             （仅 history 为 add-reducer list 时）
        ▼
LangGraph 按 channel reducer 合并进全局 state
```

### 5.4 状态合并语义速查

| 字段声明（YAML `state_schema`） | 生成的 channel | 多个节点写同一字段时 |
|---|---|---|
| `reducer: add` | `Annotated[list, operator.add]` | 列表拼接（适合 history、收集型结果） |
| `reducer: last` | `Annotated[T, _last]`（取后者） | 后写覆盖（显式声明的覆盖语义） |
| 未声明 reducer | 普通字段（LangGraph LastValue） | 后写覆盖（默认策略，C2） |
| 未在 schema 声明的字段 | 依赖基类 `ConfigDict(extra="allow")`（K2） | 节点可写，Dify 风格 |
| `history`（未声明时自动注入） | `list` + `add` reducer，可被 YAML 显式声明覆盖 | 自动累积结构化执行轨迹（C2/C4） |

## 6. 关键架构决策（ADR）

| 编号 | 决策 | 备选方案 | 理由 | 影响 |
|---|---|---|---|---|
| **ADR-001** | 动态状态模型用 **pydantic `create_model` + `extra="allow"` 基类**（K2） | (a) LangGraph 官方惯用的 `TypedDict + Annotated`；(b) dataclass | pydantic 在 DSL 边界提供运行时校验与字段 description（直接喂给 `OperatorLog`）；`extra="allow"` 支撑 Dify 风格未声明字段写入；与 `WorkflowDefinition` 同为 pydantic 生态，一致性好 | 节点拿到的是 pydantic 实例而非裸 dict，因此必须经 `convert_state_to_dict` 入口转换（R3）；动态模型无静态类型提示，靠测试与 `OperatorLog` 补可观测性 |
| **ADR-002** | **reducer 只来自 YAML 显式声明**，默认 LastValue（C2） | (a) 沿用原代码按字段名硬编码特判；(b) 要求所有字段必须显式声明 reducer | (a) 让引擎携带业务知识，违反 P2/R2，是原代码最严重的腐化点；(b) 提高 DSL 作者心智负担。显式驱动 + 清晰默认 = 通用性与便利性的平衡 | DSL 作者想累积必须写 `reducer: add`；`history` 是唯一引擎自动注入字段，语义写入文档且可覆盖 |
| **ADR-003** | 原 `graph_builder.py` **拆为 `state.py` + `graph_builder.py` + `registry.py`**（C1） | 维持单文件 | 三种职责（状态合成 / 图编译 / 运行时分发）变更频率与测试策略完全不同；单文件 815 行违反 R8，也无法单独压测 Registry 并发 | 三模块各有镜像测试文件；跨模块只通过公开 API 交互；依赖方向见 4.3 |
| **ADR-004** | Registry **每 workflow_id 一把 `threading.RLock`** 串行化 `execute_workflow`，且**日志收集改为 run-scoped，统一经 `ContextVar` 传播**（H1/H3）：`nodes/base.py` 定义模块级 `ContextVar _RUN_COLLECTOR` 与 `set_run_collector()`/`get_run_collector()`；registry 在每次 `execute_workflow` 时 set 本次运行的 `RunLogCollector` 实例（方法 `add(log)`/`collect()`），`BaseNode` 的 runnable 包装在记录日志时 `get_run_collector().add(...)` | (a) 全局单锁；(b) 无锁 + 文档声明"不支持并发"；(c) 沿用共享节点实例就地 mutate 收集日志 | (a) 不同 workflow 互相阻塞，吞吐差；(b) 进程级单例被 Web 线程池共享是既定事实，不支持并发等于埋雷；(c) 是原代码并发串扰的根因。RLock 粒度刚好；ContextVar 传播让日志与共享状态彻底解耦，节点无需反向依赖 registry | `execute_workflow` 内必须"取锁→`set_run_collector(RunLogCollector())`→invoke→`collect()`→放锁"并返回 `RunResult`；BaseNode 的 `log_execution` 等就地累积 API 仅作为兼容/调试手段，不作为运行期日志来源；收集器传播只有 ContextVar 一套方案，禁止用 `RunnableConfig.configurable` 传 key 的另一套方案，禁止 `nodes/*` 反向 import `registry`/`graph_builder`；需要并发压测（Phase 7 DoD） |
| **ADR-005** | 输出映射采用 **Dify 双写**（`{node}_result` 整包 + 逐字段平铺），带 `dual_write` 开关（默认开）（K9/C4） | (a) 只写整包；(b) 只写平铺 | 双写让下游条件路由既能写 `node_a_result.status == 'ok'` 也能写 `status == 'ok'`，兼容两类 DSL 风格；开关让对 state 体积敏感的场景可关整包 | `map_output_to_state` 行为必须文档化；history 自动追加仅在 history 为 add-reducer list 时生效，消除 str/list 二义性（C4） |
| **ADR-006** | 条件路由 no-match **显式可配置**（`raise` 默认 / `default_edge` 显式兜底），调试输出走 logging（C3） | 沿用原代码"静默落到最后一条边" | 静默兜底把配置错误伪装成正常分支，是最难排查的一类 bug；快速失败符合 P5 | DSL 需要兜底时必须显式写 default；路由器闭包禁止 `print`（C9） |
| **ADR-007** | 节点扩展走**注册表优先**的插件工厂（K5/R4） | 在 `create_node` 里堆 if/elif | 原工厂 17 个领域分支是耦合重灾区；注册表让引擎对领域节点零感知 | 内置 llm/http 保留最小分发兜底；未知类型报错信息列出已注册类型；新节点 PR 不允许改 `create_node` 分支 |
| **ADR-008** | 密钥**一律环境变量**，日志统一结构化 + redact 脱敏（C9/H6/R5） | 配置文件/YAML 携带密钥 | 原代码多处硬编码密钥与默认密码是既成事实的安全事故隐患 | `LLMConfig` 含可选字段 `api_key_env: str \| None` 与 `base_url_env: str \| None`（显式指定环境变量名），未设置时按 `llm_type` 取默认（openai → `OPENAI_API_KEY`/`OPENAI_BASE_URL`，anthropic → `ANTHROPIC_API_KEY`）；模型中绝不出现明文 `api_key` 字段，缺必需 env 密钥抛 `ConfigError`；`logging_conf.py` 提供 `RedactFilter` 脱敏过滤器；Phase 9 grep 审计 |
| **ADR-009** | HTTP 客户端用 **httpx 同步**，预留异步 | requests / aiohttp | httpx 同步与异步 API 同形，未来切 `AsyncHTTPNode` 成本最低；requests 无异步路径 | 本期禁止在 HTTPNode 内引入 asyncio 事件循环；超时必须显式配置 |
| **ADR-010** | **本期默认不引入任何缓存**；未来缓存必须 maxsize + TTL + 开关 + 文档（H4/R10） | 沿用模块级 dict 缓存 | 原 `_subgraph_cache` 无上限、永不失效、跨请求重放陈旧结果，是无界缓存反模式样本 | 代码评审 checklist 含"是否新增缓存"一项；若 Phase 4/5 引入缓存，必须补命中/失效/上限淘汰测试 |

## 8. 扩展性预留

本期不做，但当前设计为四类扩展留了明确接口。任何扩展都**不允许**破坏第 4.3 节依赖方向与 R1..R10。

### 8.1 新增节点类型

**当前预留**：`register_node_type(name, cls)` + `create_node` 注册表优先分发（K5/R4）。

**扩展方式**：在引擎包外部写 `BaseNode` 子类（实现 `build_runnable` / `validate_config`），启动时调用 `register_node_type("my_type", MyNode)`，YAML 中 `type: my_type` 即可用。引擎源码零改动。

**约束**：新节点必须遵守 R3 进出管线（`convert_state_to_dict` 进 / `map_output_to_state` 出）与 R6 显式错误处理；降级/mock 必须配置开关且有测试（H2）。

### 8.2 Send 并行扇出

**当前预留**：`_add_edges` 已按 **source 分组**处理边（K6 第 5 步的内部组织方式），条件路由已走 `add_conditional_edges(source, router, path_map)` 的统一入口（K7）。

**扩展方式**：未来 dispatcher 类节点的扇出可在 `_add_edges` 中增加一个"扇出分支"，把节点产出的任务列表经 `langgraph.types.Send` 映射为多路 `add_conditional_edges`（或 `START` 级分发），收集端配合 `reducer: add` 的 list channel 归并结果。

**约束**：扇出引入后，ADR-004 的 run-scoped 日志收集必须同步覆盖扇出的全部子任务（H3 的"覆盖本次运行实际执行的所有节点"原则）。

### 8.3 子图

**当前预留**：
1. 日志收集接口按"**覆盖本次运行实际执行的所有节点**"设计，收集逻辑通用化、与节点创建方式解耦（H3 修复原则）——子图节点即使由独立实例构建，只要接入同一收集器即可被覆盖。
2. `GraphBuilder` 不持有对 registry 的构建期快照（H5 修复原则），子图未来引用父注册表时走运行期惰性解析。

**扩展方式**：新增 `SubgraphNode`（外部注册），其 `build_runnable` 返回一个由同一 `GraphBuilder` 编译的 compiled graph；LangGraph 原生支持把 compiled graph 当节点加。

**约束**：禁止重建原代码的模块级 `_subgraph_cache`（H4）；若需缓存按 ADR-010 执行。

### 8.4 Checkpointer（持久化/断点续跑）

**当前预留**：`GraphBuilder.build_graph` 第 7 步 `compile()` 保持**无参调用**，但方法签名与调用点集中在一处，未来改为 `compile(checkpointer=...)` 只动一行。

**扩展方式**：在 `GraphBuilder` 增加可选 `checkpointer` 构造注入（默认 `None`），由 `WorkflowRegistry` 在注册时按工作流级配置传入；`execute_workflow` 增加 `thread_id` 参数透传 `config={"configurable": {"thread_id": ...}}`。

**约束**：checkpointer 选型（Memory/SQLite/Postgres）不在本期决策；引入时需评估与 ADR-004 锁粒度的交互（同一 thread_id 的并发语义）。

## 10. 隐患登记册（H1..H7）

> 全阶段统一使用 H1..H7 编号引用；修复必须落到代码 + 测试，验证列即测试验收标准。

| 编号 | 根因 | 修复 | 验证 | 所属阶段 |
|---|---|---|---|---|
| **H1** | Registry 进程级单例被 Web 线程池共享，`execute_workflow` 非原子；且在**共享节点实例**上就地 `clear_execution_history()`/读 `_execution_history` 收集日志；两个并发请求打同一 workflow_id 互相清空/覆盖历史 | 每 workflow_id 一把 `threading.RLock` 串行化 `execute_workflow`；日志收集与共享可变节点状态解耦——每次运行用 **run-scoped** `RunLogCollector` 收集日志，经 `ContextVar` 传播（ADR-004） | 多线程并发调用同一 workflow_id 的压测，断言每次运行日志完整且互不串扰 | Phase 7 |
| **H2** | 死 `try/except`（`except` 分支逻辑不可靠且从未被测试覆盖）+ 降级路径无配置开关、硬编码 mock 返回，失败路径行为不可预测 | 规范 + 落实：禁止"死 try/except"，每个 except 必须显式处理（记录 + 降级或重抛，重抛统一走 01"异常契约"异常族）；降级路径必须有测试；HTTPNode 的 retry/mock 必须显式、配置开关、经测试，mock 仅在配置显式启用时生效 | LLM/HTTP 失败路径单测（mock 抛错），断言行为符合配置 | Phase 4 / Phase 5 |
| **H3** | 日志收集不全：子图用独立节点实例且不纳入父图 `_nodes_map`，子图执行日志永远收不上来 | 原则化：收集机制必须覆盖"本次运行实际执行的所有节点"，收集逻辑通用化、与节点创建方式解耦；落地为 `RunLogCollector` + `ContextVar` 传播（ADR-004）（本期无子图，但接口预留可扩展） | 集成测试断言一次运行的 `ExecutionLog` 覆盖图中所有被执行节点 | Phase 7 |
| **H4** | 无界缓存：原模块级 `_subgraph_cache` 无上限、永不失效、读无条件写有条件，跨请求重放陈旧结果 | 本期默认不引入缓存；未来任何缓存必须 maxsize + TTL 失效 + 显式开关 + 文档 + 正确 key 设计（ADR-010） | 如实现缓存：命中/失效/上限淘汰测试 | 规范约束（Phase 4/5 若引入） |
| **H5** | 构建期快照依赖：原 AgentNode 构建时拷贝 registry 快照，之后注册的工作流不可见，产生注册顺序依赖 | 避免对可变注册表做构建期快照；需要引用其它工作流时**运行期惰性解析**；本期无 AgentNode，规范中明令禁止该反模式 | 代码评审 + 依赖方向检查（4.3：nodes 不得依赖 registry） | 规范约束 |
| **H6** | 安全/日志卫生：YAML 硬编码 API key（多处）、Neo4j 默认密码、路由闭包 print 完整 state、异常时返回硬编码 mock | 密钥一律 env；日志结构化 + redact 脱敏过滤器；禁止生产路径返回未经配置开关的硬编码 mock | grep 无硬编码密钥；日志脱敏单测；安全 checklist | Phase 8 + Phase 9 |
| **H7** | Registry API 不一致：`unregister_workflow` 与 `delete_workflow` 语义不一致导致 `_definitions`/`_nodes_map` 泄漏 | 合并为单一 `delete_workflow`，`_registry`/`_definitions`/`_nodes_map` 同增同删（C6） | 单测断言 delete 后三张映射均无残留 | Phase 7 |

## 11. 开发红线（R1..R10）

> 红线是"防跑偏"的硬性边界，详细解释与落地细则见《开发规范》文档；此处为速查基准。

| 编号 | 红线 |
|---|---|
| **R1** | 本期只实现 `BaseNode` / `LLMNode` / `HTTPNode`，禁止擅自新增节点类型或领域逻辑 |
| **R2** | 引擎保持通用，reducer 只能来自 YAML 显式声明，禁止在引擎里硬编码业务字段名 |
| **R3** | 节点必须遵循 `build_runnable` + `convert_state_to_dict` 进 / `map_output_to_state` 出 的契约，不得自行 mutate 输入 state（不可变） |
| **R4** | 新节点必须通过 `register_node_type` 注册，禁止在 `create_node` 里堆 if/elif 领域分支 |
| **R5** | 所有密钥走 env，禁止硬编码，禁止把完整 state/密钥写日志 |
| **R6** | 禁止死 try/except，错误必须显式处理 |
| **R7** | 严格 TDD（RED-GREEN-REFACTOR），单测 + 集成，覆盖率 ≥ 80% |
| **R8** | 小文件（< 400 行）小函数（< 50 行），按领域组织 |
| **R9** | pydantic v2 全量类型标注，边界处校验 |
| **R10** | 任何缓存必须有上限 + 失效 + 开关 |

**AI 协作守则（摘要）**：每阶段开工前先读本规范与架构文档；不扩大范围（scope creep 一律拒绝并记录）；遇到契约冲突（文档之间、文档与代码之间）先停下来问，不做"善意推断"。

## 12. 术语表

| 术语 | 含义 |
|---|---|
| **DSL 五元组** | `workflow_id` / `entry_point` / `nodes` / `edges` / `state_schema`，工作流 YAML 的必填骨架（K1） |
| **channel / reducer** | LangGraph 状态字段的合并策略：`add`（列表拼接）、`last`（取后者）、默认 LastValue（后写覆盖）（K3） |
| **双写（dual write）** | 节点输出同时写 `{node_name}_result` 整包与逐字段平铺（K9/C4，ADR-005） |
| **run-scoped** | 生命周期仅限单次 `execute_workflow` 调用的数据结构，与跨请求共享的节点实例相对（H1/H3 修复核心） |
| **RunLogCollector** | 运行级日志收集器，对外 `add(log)`/`collect()`，经模块级 `ContextVar` 传播（ADR-004） |
| **RunResult** | `execute_workflow` 的统一返回：`workflow_id` / `run_id` / `output` / `execution_logs` / `started_at` / `finished_at` / `duration_ms`（01 口径） |
| **异常族** | 单点定义于《01-分阶段开发计划.md · 分阶段开发计划》"异常契约"小节：基类 `WorkflowEngineError`；子类 `ConfigError` / `WorkflowNotFoundError` / `ConditionNotMatchedError` / `LLMNodeError` / `HTTPNodeError`。场景映射：路由无命中 → `ConditionNotMatchedError`；未知 workflow_id → `WorkflowNotFoundError`；缺必需 env 密钥 → `ConfigError`；LLM 调用失败 → `LLMNodeError`；HTTP 调用失败 → `HTTPNodeError` |
| **redact** | 日志脱敏：对密钥、完整 state 等敏感内容做掩码后再输出的过滤器（C9/H6） |
| **构建期 vs 运行期** | 构建期 = 注册时编译图（一次）；运行期 = `invoke` 执行（多次）。禁止构建期快照可变注册表（H5） |
| **DoD** | Definition of Done，阶段完成的定义 |
| **ADR** | Architecture Decision Record，架构决策记录（第 6 章） |
