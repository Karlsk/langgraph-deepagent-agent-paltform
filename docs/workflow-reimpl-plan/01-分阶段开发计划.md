## A 总览

### A.1 项目目标与分期策略

在新项目中重新实现一个**精简、生产级**的声明式工作流引擎：

- **输入**：声明式 YAML（五元组 DSL：`workflow_id` / `entry_point` / `nodes` / `edges` / `state_schema`，K1）。
- **内核**：LangGraph 状态图编译器（`StateGraph` / `START` / `END`）+ 进程级注册运行时（`WorkflowRegistry`）。
- **本期节点**：只实现 3 个——抽象 `BaseNode` + 具体 `LLMNode` + `HTTPNode`（R1）。其余 17 种领域节点、子图嵌套、`langgraph.types.Send` 并行扇出、Neo4j 计划生成等**一律列为"未来扩展"，本期不做**。
- **技术栈（统一口径）**：Python 3.11+；`langgraph` + `langchain_core`；`pydantic` v2；`httpx`（同步，预留异步）；`langchain_openai` / `langchain_anthropic`；`pytest` + `pytest-cov`；`black` / `isort` / `ruff`；密钥一律环境变量。

分期策略是**严格自底向上的单向依赖链**：模型 → 状态 → 节点 → 图 → 运行时 → 入口 → 加固。除 Phase 4/5 可并行外，其余阶段串行。每个阶段独立可验收（DoD 闭环），任何阶段失败都不应污染已完成阶段的产出。

### A.4 贯穿全程的 TDD 总则

严格遵循红线 R7 与《02·开发规范》：

1. **RED → GREEN → REFACTOR 循环**，每个行为变更先有失败测试：
   - RED：先写一个最小的失败测试（`pytest` 运行确认真的失败，而不是报错）。
   - GREEN：写刚好让测试通过的最少实现，允许丑陋。
   - REFACTOR：在测试保护下重构，满足 R8（小文件 < 400 行、小函数 < 50 行）与不可变原则。
2. **测试分层与标记**：
   - `@pytest.mark.unit`：纯函数/类级测试，不起网络、不起子进程、毫秒级。
   - `@pytest.mark.integration`：跨模块协作（YAML→图→执行）、并发压测。
   - `pytest.ini`/`pyproject.toml` 注册这两个 marker，CI 中先跑 unit 再跑 integration。
3. **Mock 规范**（详见《02·开发规范》）：
   - **禁止真实网络调用**：LLM 一律 mock `langchain_openai.ChatOpenAI` / `langchain_anthropic.ChatAnthropic`（monkeypatch 或依赖注入实例）；HTTP 一律用 `httpx.MockTransport` 或 monkeypatch `httpx.request`。
   - 重试测试必须 monkeypatch `time.sleep`，**不允许测试真实睡眠**。
   - 共享可变的全局状态（如 `factory._NODE_REGISTRY`）必须有 autouse fixture 做"快照-恢复"，防止测试串扰（见 D7）。
4. **覆盖率**：逐阶段累计，Phase 9 总覆盖率 `>= 80%`（`pytest --cov=workflow_engine --cov-report=term-missing`）。每个阶段的失败路径（except 分支、校验失败分支）必须被覆盖——这是 H2 的验证手段。
5. **断言风格**：断言行为而非实现；异常断言用 `pytest.raises(XxxError, match="...")` 同时校验类型与消息要点。
6. **先写哪些测试**：每个阶段的"TDD 测试要点"小节给出清单；原则上**契约（签名/校验/错误）测试先于快乐路径测试**。

除各阶段自带的 DoD 外，**每个阶段都必须满足以下通用条款**，缺一不可：

| # | 通用 DoD 条款 | 验证命令/方式 |
| --- | --- | --- |
| G1 | 任务清单 checkbox 全部勾选，且每项有对应提交 | `git log` 对照清单 |
| G2 | 该阶段全部测试绿（unit + 涉及的 integration） | `pytest -m unit` / `pytest -m integration` |
| G3 | 格式化与 lint 零问题 | `black --check .`、`isort --check .`、`ruff check .` |

### A.6 如何把单个 Phase 交给 AI 执行

本计划的目标读者包括 AI 编码代理。按如下流程把**单个阶段**委派出去（一次只派一个阶段，避免上下文膨胀与范围蔓延）：

**第 1 步 · 会话预热（强制阅读）**。在新会话开头给出三份材料：

1. 本文档对应 Phase 的完整小节（含任务清单、接口契约、TDD 要点、DoD、隐患修复）。
2. 《00·架构总览》中与本阶段模块对应的章节。
3. 《02·开发规范》全文（红线 R1..R10 在其中）。

**第 2 步 · 使用统一的任务提示词模板**：

```text
你正在实现"工作流引擎重实现"项目的 Phase {N}（{阶段名}）。

【强制阅读】
- docs/workflow-reimpl-plan/01-分阶段开发计划.md 的 Phase {N} 全节
- docs/workflow-reimpl-plan/00-架构总览.md（架构总览）相关模块
- docs/workflow-reimpl-plan/02-开发规范.md（红线 R1..R10）

【边界（违反即失败）】
- 只做 Phase {N} 任务清单中的条目，不提前实现后续阶段
- 接口签名必须与计划文档"接口契约"小节逐字一致；发现契约冲突：停下，先提问，不得自行折中
- 不新增节点类型、不硬编码业务字段名、不硬编码密钥（R1/R2/R5）

【流程】
1. 严格 TDD：先写失败测试并运行确认 RED → 最小实现 GREEN → 重构
2. 每完成一个任务清单项即运行：pytest -m unit、ruff check、black --check
3. 每个任务清单项对应 1~N 个 conventional commit

【交付物】
- 代码 + 测试 + DoD 逐条自评表（G1..G8 + 阶段专属 DoD）
- 结尾给出"偏离与疑问清单"（若无偏离写"无"）
```

**第 3 步 · 验收**（人类或评审代理）：

1. 运行该阶段全部测试与 lint。
2. 逐条核对 DoD 自评表，重点抽查：失败路径是否有测试（H2）、日志是否泄露 state/secret（H6）、是否有范围蔓延（R1）。
3. 对照"接口契约"小节核对公开签名——**签名是跨阶段合同，偏差必须打回**。

**AI 协作守则（摘自契约，每阶段重申）**：每阶段先读本规范与架构文档；不扩大范围；遇到契约冲突先问；不确定时宁可停下来提问，也不要"自作主张地兼容"。

from typing import Annotated, Any

TYPE_MAP: dict[str, Any] = {
    "str": str, "int": int, "float": float, "bool": bool,
    "list": list, "dict": Any, "object": Any, "any": Any,
    "List[str]": list, "Dict[str, Any]": Any,
}

def _last(a: Any, b: Any) -> Any:
    """reducer='last' 的合并函数：后写覆盖。"""

class StateModelFactory:
    """动态状态模型工厂（单一职责，落实 C1 拆分）。"""

    @staticmethod
    def create_state_model(
        state_schema: dict[str, StateFieldSchema],
    ) -> type[BaseModel]:
        """把 state_schema 合成为动态 Pydantic 模型。

        - reducer='add'  -> Annotated[list, operator.add]（列表合并 channel）
        - reducer='last' -> Annotated[T, _last]（后写覆盖 channel）
        - 未声明 reducer  -> 普通字段（LangGraph LastValue，后写覆盖）

        - 基类 ConfigDict(extra='allow')，允许节点写未声明字段（K2）
        Raises:
            ValueError: type 字符串不在 TYPE_MAP 中。
        """

## D 风险与注意事项

### D1 langgraph 版本兼容

- **风险**：`langgraph` 迭代快，`StateGraph` 对 pydantic 模型的 channel 推断、`add_conditional_edges` 的 `path_map` 语义、`compile()` 返回类型、`START`/`END` 的导入路径在不同主版本间存在差异。
- **影响**：Phase 2/6/7 的集成测试可能在新版本上批量失败。
- **缓解**：Phase 0 即在 `pyproject.toml` pin 主版本区间（实现时以"当前稳定版"为准，如 `langgraph>=0.2,<0.7`，`langchain-core` 与之配套）；集成测试中只依赖公开 API（`StateGraph` / `add_node` / `add_edge` / `add_conditional_edges` / `set_entry_point` / `compile` / `invoke`），不依赖内部属性；升级依赖作为独立 `chore:` 提交并跑全量集成测试。

### D2 pydantic v2 create_model + Annotated reducer 写法陷阱

- **风险**：动态模型是引擎地基，常见坑包括：
  1. 字段定义必须是二元组 `(annotation, FieldInfo)`，`Annotated[list, operator.add]` 要放在 annotation 位置，reducer 才会被 langgraph 识别为 channel；
  2. `default` 与 `default_factory` 不可同时给，可变默认（list）必须 `default_factory=list`；
  3. v2 中 `create_model` 的 `__config__` 已弃用，`extra="allow"` 必须通过 `__base__` 继承一个带 `model_config = ConfigDict(extra="allow")` 的基类实现；
  4. `Annotated[T, reducer]` 中的 reducer 必须是可调用对象，`typing.get_type_hints(model, include_extras=True)` 可用于测试内省。
- **影响**：reducer 不生效会导致状态合并行为静默错误（最难排查的一类 bug）。
- **缓解**：Phase 2 的集成测试（真实 `StateGraph` 跑 add/last channel）是强制 DoD；单测用 `typing` 内省断言 reducer 元数据；把"正确写法"固化为 `state.py` 中的注释样板。

### D3 并发锁粒度与 ContextVar 传播

- **风险**：per-workflow `RLock` 串行化保证正确性，但若未来单 workflow 内部有长耗时节点（LLM 调用），会成为吞吐瓶颈；另外 `contextvars` 在线程池下按线程隔离（安全），但在 `asyncio` 任务间会随 `Task` 复制传播——本期同步实现无此问题，**预留的异步路径重新启用时必须重新评审收集器传播语义**。
- **影响**：吞吐受限；异步化时若误用可能导致跨运行日志串扰。
- **缓解**：锁粒度决策写入 `registry.py` 类 docstring；并发压测（Phase 7/9）同时断言"不同 workflow 并发不互相阻塞"；异步化列入"未来扩展"清单并要求单独设计评审。

### D4 httpx 同步实现与超时

- **风险**：本期 `httpx.request` 同步调用会阻塞工作线程；`timeout` 必须显式（默认 30s 可配），否则慢端点会拖垮整个 registry 串行链。
- **缓解**：`HTTPNodeConfig.timeout` 必填默认值且 `gt=0`；重试退避只在显式 `retry_on_status` 命中时发生；README 注明"高并发 HTTP 编排请评估异步扩展"。

### D5 测试时间控制

- **风险**：重试退避若真实 sleep，单测套件从秒级膨胀到分钟级，且引入 flaky。
- **缓解**：Phase 4/5 的 `_invoke_with_retry` / HTTP 重试统一通过模块内 `time.sleep` 引用，测试一律 monkeypatch 为计数器；退避数值用断言覆盖（`1, 2, 4` 序列）。

### D6 YAML 安全

- **风险**：`yaml.load` 可反序列化任意 Python 对象（远程代码执行面）。
- **缓解**：全仓库只允许 `yaml.safe_load`；Phase 1 的解析函数 docstring 明示；ruff 可启用相应规则或在代码审查清单中固定该项。

### D7 全局注册表的测试隔离

- **风险**：`factory._NODE_REGISTRY` 是模块级全局可变状态，测试中注册的假节点会污染后续用例（偶发失败根源）。
- **缓解**：Phase 3 提供 autouse fixture `restore_node_registry`（快照-恢复）；任何新增全局状态（如未来缓存）必须配套同类 fixture，并在《02·开发规范》测试章节登记。

### D8 范围蔓延（最大的流程风险）

- **风险**：原仓库有 19 种节点与大量领域逻辑，实现者（人或 AI）容易"顺手"移植 dispatcher/subgraph/planner 等，或把 `circle_*` 领域字段名特判悄悄带回 `state.py`。
- **缓解**：红线 R1/R2 + 每阶段守护测试（`test_no_hardcoded_field_names`、`grep` 零命中项、`NodeType` 成员数断言）+ A.6 的 AI 委派模板把边界写成失败条件；代码审查第一问永远是"这个改动在任务清单里吗？"
