### H1 并发不安全：Registry 共享可变状态

#### 原代码问题

原 `WorkflowRegistry`（`graph_builder.py` L526 起）是进程级单例，被 Web 线程池共享，但存在两处共享可变状态竞争：

1. **`execute_workflow` 非原子**（L623-651）：

```python
# 原代码（节选，graph_builder.py L623-651）
def execute_workflow(self, workflow_id, input_data):
    workflow = self.get_workflow(workflow_id)
    nodes_map = self._nodes_map.get(workflow_id, {})
    for node_name, node in nodes_map.items():
        node.clear_execution_history()          # ← 在“共享节点实例”上就地清空
    try:
        result = workflow.invoke(input_data)
        self._collect_execution_logs(workflow_id) # ← 再从共享实例收集
        return result
    ...
```

2. **节点实例持有可变执行历史**（`node/base.py` L42, L68-78）：

```python
# 原代码（节选，node/base.py）
self._execution_history: list[ExecutionLog] = []   # 实例级可变列表，跨请求共享
def log_execution(self, execution_log): self._execution_history.append(execution_log)
def clear_execution_history(self): self._execution_history.clear()
```

而节点实例由 `_nodes_map[workflow_id]` 长期持有、跨请求复用（`graph_builder.py` L166 注入）。失败时序示例：

| 时刻 | 请求 A（workflow `w1`） | 请求 B（workflow `w1`） |
|------|--------------------------|--------------------------|
| t0 | `clear_execution_history()` 清空所有节点 | |
| t1 | `invoke()` 执行节点 n1，写入日志 A1 | `clear_execution_history()` **清空 A1** |
| t2 | 执行 n2，写入 A2 | 执行 n1，写入 B1 |
| t3 | `_collect_execution_logs()` → 收到 {A2, B1}，**缺 A1、混入 B1** | |
| t4 | | `_collect_execution_logs()` → 覆盖 `definition.execution_history` |

同类问题还有 `LLMNode.messages`（`llm_node.py` L150-164 的 `set_messages/add_message/clear_messages`）——任何"节点实例上的可变字段在运行期被改写"的写法都属于这一族。

#### 根因分析

- **生命周期错配**：`_execution_history` 是"单次运行"的数据，却寄生在"与注册表同生命周期"的共享节点实例上。
- **收集机制依赖就地 mutate**：`execute_workflow` 用 "先 clear → invoke → 再 collect" 的三步非原子序列模拟运行级隔离，三步之间任何并发插入都会串扰。
- **`definition.execution_history` 单槽位**：整个工作流只有一份执行历史，后写覆盖前写，天然不支持并发。

#### 修复方案

两件事一起做：**(1) per-workflow 可重入锁串行化执行**（纵深防御）；**(2) 运行级 collector 承接日志**（根治）。落点 `workflow_engine/registry.py` 与 `workflow_engine/nodes/base.py`。

**Step 1 — 运行级日志收集器与 ContextVar（`nodes/base.py` 定义，`registry.py` 使用）**

收集器经 `nodes/base.py` 的模块级 ContextVar 按运行传递（唯一方案；**禁止**用 `RunnableConfig` `configurable` 传 key 的另一套方案，**禁止** `nodes/*` 反向 `import` `registry`/`graph_builder`——依赖方向只能是 registry → nodes）：

```python
# workflow_engine/nodes/base.py（示意）
from contextlib import contextmanager
from contextvars import ContextVar, Token
from typing import Iterator, Protocol

class RunLogCollectorLike(Protocol):
    def add(self, log: ExecutionLog) -> None: ...
    def collect(self) -> list[ExecutionLog]: ...

_RUN_COLLECTOR: ContextVar[RunLogCollectorLike | None] = ContextVar(
    "workflow_engine_run_collector", default=None
)

def set_run_collector(collector: RunLogCollectorLike | None) -> Token: ...
def get_run_collector() -> RunLogCollectorLike | None: ...

@contextmanager
def use_run_collector(collector: RunLogCollectorLike | None) -> Iterator[None]:
    """registry.execute_workflow 进出场使用；finally 复位，保证 ContextVar 不泄漏到后续请求。"""
    token = set_run_collector(collector)
    try:
        yield
    finally:
        set_run_collector(token.old_value)  # 等价于 reset token
```

```python
# workflow_engine/registry.py（示意）
import threading, uuid
from dataclasses import dataclass, field
from datetime import datetime

from workflow_engine.models import ExecutionLog

@dataclass
class RunLogCollector:
    """运行级（run-scoped）执行日志收集器。
    每次 execute_workflow 新建一个，经 nodes/base.py 的 ContextVar 对全部节点可见。
    不依赖节点创建方式，凡遵循 BaseNode 约定的节点都会被覆盖（支撑 H3）。
    """
    run_id: str
    _logs: list[ExecutionLog] = field(default_factory=list)
    _guard: threading.Lock = field(default_factory=threading.Lock)

    def add(self, log: ExecutionLog) -> None:
        with self._guard:
            self._logs.append(log)

    def collect(self) -> list[ExecutionLog]:
        """按时间排序的副本；调用方不可变。"""
        with self._guard:
            return sorted(self._logs, key=lambda x: x.timestamp)
```

`execute_workflow` 的返回信封统一为 **`RunResult`**（`@dataclass(frozen=True)`），字段 `{workflow_id, run_id, output, execution_logs, started_at, finished_at, duration_ms}`，**签名与字段以《01-分阶段开发计划.md · 分阶段开发计划》Phase 7 接口契约为准**；`duration_ms` 为只读属性。

**Step 2 — Registry 双锁结构（`registry.py`）**

```python
class WorkflowRegistry:
    def __init__(self) -> None:
        # 三张核心映射：同增同删（见 H7）
        self._registry: dict[str, Any] = {}                       # workflow_id -> compiled graph
        self._definitions: dict[str, WorkflowDefinition] = {}     # workflow_id -> definition
        self._nodes_map: dict[str, dict[str, BaseNode]] = {}      # workflow_id -> {name: node}
        # H1：运行锁表 + 结构守卫锁
        self._run_locks: dict[str, threading.RLock] = {}
        self._guard = threading.Lock()      # 保护四张表的结构变更（register/update/delete）
        self._graph_builder = GraphBuilder()

    def _run_lock(self, workflow_id: str) -> threading.RLock:
        """同一 workflow_id 串行化执行；不同 workflow_id 互不阻塞。
        选 RLock：为未来 AgentNode 嵌套调用同一工作流预留可重入能力。"""
        with self._guard:
            lock = self._run_locks.get(workflow_id)
            if lock is None:
                lock = threading.RLock()
                self._run_locks[workflow_id] = lock
            return lock

    def register_workflow(self, definition: WorkflowDefinition) -> str:
        with self._guard:                                   # 结构变更原子化
            compiled, nodes_map = self._graph_builder.build_graph(definition)
            self._definitions[definition.workflow_id] = definition
            self._registry[definition.workflow_id] = compiled
            self._nodes_map[definition.workflow_id] = nodes_map
            return definition.workflow_id

    def execute_workflow(
        self,
        workflow_id: str,
        input_data: dict[str, Any],
        *,
        run_id: str | None = None,
    ) -> RunResult:
        workflow = self.get_workflow(workflow_id)           # 不存在 → WorkflowNotFoundError（01 异常契约）
        definition = self._definitions[workflow_id]
        run_id = run_id or uuid.uuid4().hex
        collector = RunLogCollector(run_id=run_id)
        started = datetime.now()
        with self._run_lock(workflow_id):                   # H1：串行化同一 workflow
            # 全程不调用任何 node.clear_execution_history()
            try:
                with use_run_collector(collector):          # 进场设置、出场复位 ContextVar
                    output = workflow.invoke(input_data)
            finally:
                logs = collector.collect()                  # 运行级快照，天然隔离
                definition.execution_history = logs         # 单槽位：只保留最近一次运行（RC12）
        return RunResult(                                   # 字段以 01 接口契约为准
            workflow_id=workflow_id,
            run_id=run_id,
            output=output,
            execution_logs=logs,
            started_at=started,
            finished_at=datetime.now(),
        )                                                   # duration_ms 为只读属性
```

**Step 3 — 节点侧经 ContextVar 写 collector，绝不 mutate 实例（`nodes/base.py`）**

以下模板方法写法为**示例说明（非契约）**：`BaseNode` 的契约形态（`build_runnable()` 抽象、子类各自实现 `func(state)->dict`、辅助函数 `wrap_runnable(name, func) -> RunnableLambda(func).with_config(tags=[name])`）以《01-分阶段开发计划.md · 分阶段开发计划》/《02-开发规范.md · 开发规范》为准。无论哪种形态，日志记录点都通过本模块的 `get_run_collector()` 取收集器（**不 import `registry`/`graph_builder`**，不依赖任何 config 传参）：

```python
# workflow_engine/nodes/base.py（示意）
from langchain_core.runnables import Runnable, RunnableLambda
from workflow_engine.utils import convert_state_to_dict, map_output_to_state

class BaseNode(ABC):
    # K4 接口签名保留；语义调整：生产运行写入 run-scoped collector，
    # 实例缓冲仅用于“无 collector 的独立调试”场景。execute_workflow 永不 clear。
    def __init__(self, name, node_type, config, operator_log=None):
        ...
        self._execution_history: list[ExecutionLog] = []   # 仅独立调试缓冲（保留 K4）

    @abstractmethod
    def execute(self, state_dict: dict[str, Any]) -> dict[str, Any]:
        """子类实现纯业务：读 dict、返回 dict。禁止 mutate 入参（R3）。"""

    def log_execution(self, execution_log: ExecutionLog) -> None:
        """双写：实例历史（调试）+ 当前 ContextVar 收集器（运行级权威，若存在）。"""
        self._execution_history.append(execution_log)
        collector = get_run_collector()                    # 本模块 ContextVar，零反向依赖
        if collector is not None:
            collector.add(execution_log)

    def build_runnable(self) -> Runnable:                  # 示例形态；契约以 01/02 为准
        self.validate_config()

        def runner(state: Any) -> dict[str, Any]:
            state_dict = convert_state_to_dict(state)      # 进：统一状态转 dict
            t0 = time.perf_counter()
            error: str | None = None
            output: dict[str, Any] = {}
            try:
                output = self.execute(state_dict)
                return map_output_to_state(self.name, output, state_dict)  # 出：双写映射
            except Exception as e:                          # R6：显式处理，禁止裸 pass
                error = str(e)
                logger.error("node '%s' failed: %s", self.name, e, exc_info=True)
                raise
            finally:
                self.log_execution(ExecutionLog(
                    node_name=self.name,
                    node_type=self.node_type,
                    input_data=_redact_for_log(state_dict),   # H6：日志不落完整敏感态
                    output_data=_redact_for_log(output),
                    execution_time_ms=(time.perf_counter() - t0) * 1000,
                    error=error,
                ))

        return RunnableLambda(runner).with_config(tags=[self.name])
```

要点：
- `runner` 内**没有任何对 `self` 可变字段的直接写操作**（运行级收集由 `log_execution` 经 ContextVar 完成，collector 是每次运行由 registry 设置的线程/任务局部状态）。
- LLMNode/HTTPNode 只实现 `execute(state_dict) -> dict`，不再各自拼 `log_execution` 模板，消除复制粘贴错误面（H2 的结构性预防）。
- `_redact_for_log` 复用 `logging_conf.py` 的脱敏工具（H6）。
- 依赖方向红线：`nodes/base.py` **只定义** ContextVar 与收集器接口，**禁止** `import registry`/`graph_builder`；设置动作只发生在 `registry.execute_workflow`。

### H2 死异常兜底：except 分支逻辑不可靠且从未被测试覆盖

#### 原代码问题

`node/worker.py` 的 `worker_func` 外层兜底（L262-285）：

```python
# 原代码（节选，node/worker.py L262-285）
except Exception as e:
    # ... TODO: 【测试阶段临时 Mock 数据 / 生产上线删除】 ...
    logger.warning(f"[{self.name}] 控制器/MCP 服务不可达或执行异常 ({e})，使用测试阶段 Mock 兜底数据")
    # ... 构造 mock output 并返回 ...
```

该 `except` 分支是**死 try/except**：分支内部逻辑不可靠（历史分析曾归因为"引用未导入的 `logger` 抛 `NameError`"，但当前代码 `worker.py` 已有 `import logging` 与模块级 logger，该细节在现网代码**不可复现**——行号与细节以语义为准），且失败路径**从未被任何测试覆盖**，分支真实行为无人验证。同时，兜底返回的 mock 是硬编码领域话术（"业务流量已安全切流隔离"），**无任何配置开关**，一旦进入即掩盖真实故障。

同一族问题还包括：
- `node/http.py` 的 `HTTPNodeConfig.mock_responses`（`models.py` L170）声明了却**从未接线**——死配置，行为不可预期；
- 兜底/降级行为写在注释 TODO 里而非配置里，"临时方案"永久化（与 H6 交叉）。

#### 根因分析

- **死 try/except 反模式**：except 分支逻辑不可靠，且从未被测试覆盖——失败路径从未被真正执行过，其行为完全不可预期。
- **降级路径无配置开关、硬编码 mock 返回**：降级/mock 行为与配置脱节，返回硬编码业务话术，真实故障被静默掩盖。
- **缺少统一的错误出口约定**：每个节点各写各的 try/except，错误处理质量依赖个人自觉。

#### 修复方案

**规范层（写入《02 · 开发规范》，红线 R6）**：

1. 每个 `except` 必须显式**记录 + 重抛**：`logger.error(..., exc_info=True)` 后 `raise XxxError(...) from e`（异常族以《01-分阶段开发计划.md · 分阶段开发计划》异常契约为唯一来源，见下文）；**不引入失败降级（degrade）路径**，失败一律显式报错。
2. **禁止裸 `except:` / `except Exception: pass`**；禁止在 except 中 `return` 一个与配置无关的硬编码值。
3. except 分支内**只允许使用已导入的名字**——这一条由 R7 的失败路径单测兜底（只要跑过就不会有未定义名字的问题）。

**异常族（单点定义于《01-分阶段开发计划.md · 分阶段开发计划》异常契约小节）**：基类 `WorkflowEngineError(Exception)`；子类 `ConfigError`、`WorkflowNotFoundError`、`ConditionNotMatchedError`、`LLMNodeError`、`HTTPNodeError`。场景映射：路由无命中 → `ConditionNotMatchedError`；未知 `workflow_id` → `WorkflowNotFoundError`；缺必需 env 密钥 → `ConfigError`；LLM 调用失败 → `LLMNodeError`；HTTP 调用失败 → `HTTPNodeError`。本文及实现不得另造互不兼容的异常定义。

**结构层（H1 的模板方法已解决 80%）**：日志记录、计时、`ExecutionLog` 落盘全部收敛到 `BaseNode.build_runnable` 的 `runner`，子类 `execute` 只需专注业务；子类需要重试用节点配置内的扁平字段驱动（见下）。

**重试（扁平字段承载，不引入共享 RetryPolicy 模型）**：重试参数由节点配置内的扁平字段 `max_retries` / `retry_base_delay`（指数退避）承载，字段定义以《01-分阶段开发计划.md · 分阶段开发计划》接口契约为准（HTTPNodeConfig：`max_retries: int = Field(default=0, ge=0)`、`retry_base_delay: float = Field(default=1.0, gt=0)`、`retry_on_status: list[int]`）。节点内退避循环的分支语义示意（仅分支语义为契约）：

```python
# workflow_engine/nodes/http_node.py（示意，分支语义）
def _invoke_with_retry(self, send: Callable[[], httpx.Response]) -> httpx.Response:
    attempt = 0
    while True:
        resp = send()
        if resp.status_code not in self.node_config.retry_on_status:
            return resp
        if attempt >= self.node_config.max_retries:               # 默认 0 = 不重试
            resp.raise_for_status()
        wait = self.node_config.retry_base_delay * (2 ** attempt)  # 指数退避
        logger.warning("node '%s' retry in %.2fs (status=%d)", self.name, wait, resp.status_code)
        time.sleep(wait)
        attempt += 1
```

**HTTPNode 错误出口（`nodes/http_node.py`，Phase 5 落地）**：字段集以《01-分阶段开发计划.md · 分阶段开发计划》Phase 5 接口契约为唯一基准（`{url, method, headers, body_template, response_path, timeout, max_retries, retry_base_delay, retry_on_status, mock_enabled, mock_responses}`）：

```python
class HTTPNodeConfig(BaseModel):
    url: str
    method: Literal["GET", "POST", "PUT", "DELETE"] = "POST"
    headers: dict[str, str] | None = None
    body_template: str | None = None
    response_path: str | None = None
    timeout: float = Field(default=30.0, gt=0)                    # 字段名统一 timeout
    max_retries: int = Field(default=0, ge=0)                     # 扁平重试字段，默认不重试
    retry_base_delay: float = Field(default=1.0, gt=0)
    retry_on_status: list[int] = [429, 500, 502, 503, 504]
    mock_enabled: bool = False                                    # H2/H6：默认关，显式开才生效
    mock_responses: dict[str, str] | None = None                  # 仅 mock_enabled=True 时使用
    # 无 on_failure / degrade_output：不引入失败降级，失败显式报错

class HTTPNode(BaseNode):
    def execute(self, state_dict: dict[str, Any]) -> dict[str, Any]:
        rendered = self._render(state_dict)                 # url/headers/body 占位符渲染
        if self.node_config.mock_enabled:                   # 唯一的 mock 入口，配置驱动
            try:
                raw = self.node_config.mock_responses[self._mock_key(rendered)]
            except (KeyError, TypeError) as e:
                raise HTTPNodeError(                        # mock 未命中 → 显式报错，禁止静默回退真实调用
                    f"node '{self.name}': mock miss for {rendered.url}"
                ) from e
            return self._extract(json.loads(raw))
        try:
            resp = self._invoke_with_retry(                 # retry_on_status 命中时指数退避
                lambda: self._send_once(rendered)           # 429/5xx/超时/连接错误按配置重试
            )
            resp.raise_for_status()
        except Exception as e:                              # noqa: BLE001 - 显式重抛
            raise HTTPNodeError(                            # 记录由 runner 统一做
                f"node '{self.name}': HTTP {rendered.method} {rendered.url} failed: {e}"
            ) from e
        return self._extract(resp.json())                   # response_path 提取
```

### H3 执行日志收集不全：收集范围与节点创建方式耦合

#### 原代码问题

原收集逻辑只遍历父图的 `_nodes_map`（`graph_builder.py` L660-683）：

```python
# 原代码（节选，graph_builder.py L671-677）
nodes_map = self._nodes_map.get(workflow_id, {})
for node_name, node in nodes_map.items():
    node_logs = node.get_execution_history()
    execution_history.extend(node_logs)
```

而子图内部节点由 `_build_and_inject_subgraph`（L414-456）用**独立的 `create_node` 调用**创建，只注入进子图，**从不登记进父图 `_nodes_map`**：

```python
# 原代码（节选，graph_builder.py L434-437）
for sn_def in sub_node_defs:
    sn = create_node(sn_def, workflow_registry=available_workflows)
    sub_graph.add_node(sn_def.name, sn.build_runnable())   # sn 没有任何 map 持有它
```

结果：子图内部节点（如循环里的 planner/reflection/worker）产生的 `ExecutionLog` 永远收集不上来，审计链路存在黑洞。该缺陷的**结构**比"子图"本身更危险：任何"非标准方式创建的节点"都会从审计中消失。

#### 根因分析

- 收集机制回答的是"**注册表里有哪些节点**"，而不是"**本次运行执行了哪些节点**"——问题域错位。
- 收集依赖 `_nodes_map` 这份"构建期清单"，与节点创建路径强耦合；每新增一种节点装配方式就要改收集代码。

#### 修复方案

把收集从"遍历构建期清单"改为"**运行期自然汇聚**"：H1 引入的 `RunLogCollector` 经 `nodes/base.py` 的模块级 ContextVar 对全图可见，本次运行中**每一个被执行的节点**在记录日志时都通过 `get_run_collector().add(...)` 汇入同一收集器（未来引入子图时同样适用——收集与图结构无关）。因此：

- 只要节点遵循 `BaseNode` 约定（日志记录点经 `log_execution` 双写到当前 ContextVar 收集器），**被执行即被收集**，与创建方式无关；
- `WorkflowRegistry` 不再为收集而遍历 `_nodes_map`（`_nodes_map` 仅供 `get_node_by_name` 等查询接口使用）；
- 预留可扩展性：收集器接口只有 `add(log)` / `collect()`，未来子图节点/并行扇出节点无需任何收集侧改造。

```python
# workflow_engine/registry.py（示意）——收集即取快照，零遍历
def execute_workflow(self, workflow_id, input_data, *, run_id=None) -> RunResult:
    ...
    collector = RunLogCollector(run_id=run_id)
    with self._run_lock(workflow_id):
        try:
            with use_run_collector(collector):      # ContextVar 进场设置、出场复位
                output = workflow.invoke(input_data)
        finally:
            definition.execution_history = collector.collect()  # 单槽位：失败运行也留最近一次
    logs = definition.execution_history             # 覆盖本次运行实际执行的所有节点
    return RunResult(workflow_id=workflow_id, run_id=run_id, output=output,
                     execution_logs=logs, started_at=started, finished_at=datetime.now())
```

**执行历史只保留单槽位**：`definition.execution_history` 仅保存**最近一次运行**的日志，`get_execution_history` 返回之。**不引入** `_run_history` 环形缓冲 / `_archive_run` / `last_run_logs()` 等多运行归档设计（避免无界增长，呼应 H4 精神）。

**一致性自检钩子（可选增强，Phase 7）**：运行结束后，用 collector 收到的 `node_name` 集合与 `definition` 中"静态可达节点集合"对比，若出现"图中存在、路径应经过、却无日志"的节点，记一条 `WARNING`（不阻断）。本期无子图，该校验主要用于捕获条件分支覆盖率。

### H4 无界缓存：模块级 dict 永不失效

#### 原代码问题

`node/subgraph_node.py` 的模块级缓存（L29-31, L66-68, L87-90）：

```python
# 原代码（节选）
_subgraph_cache: Dict[str, list] = {}              # 模块级、进程内、无上限、永不失效
...
if cache_key in _subgraph_cache:                   # 读：无条件
    return {output_field: _subgraph_cache[cache_key]}   # 直接重放，可能陈旧
...
if runbook_id and device:                          # 写：有条件
    _subgraph_cache[cache_key] = output_val
```

四个问题叠加：
1. **无上限**：key 随 `event_id:runbook_id:device` 组合膨胀，内存无界增长；
2. **永不失效**：无 TTL，上游数据更新后仍重放旧结果；
3. **读写条件不对称**：无条件读 + 有条件写，语义难以推理；
4. **隐式跨请求共享**：无开关、无文档、调用方完全不知情。

#### 根因分析

把"性能优化手段"当成了"默认行为"，且绕过一切配置与文档直接内嵌进节点逻辑。缓存作为横切关注点，没有显式契约（开关/上限/失效/key 规范）就必然失控。

#### 修复方案

**本期决策：不引入任何缓存**（子图整体丢弃，LLMNode/HTTPNode 直连）。将以下契约作为**强制规范**写入《02 · 开发规范》（红线 R10），约束 Phase 4/5 及未来任何实现：

任何缓存必须同时满足，缺一不得合入：

| 维度 | 强制要求 |
|------|----------|
| 上限 | 显式 `maxsize`，达到上限按 LRU 淘汰 |
| 失效 | 显式 TTL（秒），过期条目惰性删除 |
| 开关 | 配置字段 `cache_enabled: bool = False`，默认关 |
| key | key 设计文档化；必须由**规范化后的完整请求语义**哈希而来（不得只用部分字段） |
| 可观测 | 命中率计数 + `cache_hit/cache_miss` 结构化日志 |
| 隔离 | 缓存实例归属节点配置或注册表，**禁止模块级裸 dict** |

参考实现骨架（仅在未来需要时落盘，建议放 `workflow_engine/nodes/base.py` 旁的小工具或节点内部，不新增顶层模块）：

```python
class TTLCache(Generic[K, V]):
    """有上限 + TTL 的最小缓存。线程安全。仅作未来实现参考，本期不落盘。"""
    def __init__(self, maxsize: int = 256, ttl_seconds: float = 300.0):
        self._maxsize, self._ttl = maxsize, ttl_seconds
        self._data: OrderedDict[K, tuple[float, V]] = OrderedDict()
        self._guard = threading.Lock()

    def get(self, key: K) -> V | None:
        with self._guard:
            item = self._data.get(key)
            if item is None:
                return None
            ts, val = item
            if time.monotonic() - ts > self._ttl:           # 惰性失效
                del self._data[key]
                return None
            self._data.move_to_end(key)                     # LRU
            return val

    def set(self, key: K, val: V) -> None:
        with self._guard:
            self._data[key] = (time.monotonic(), val)
            self._data.move_to_end(key)
            while len(self._data) > self._maxsize:          # 上限淘汰
                self._data.popitem(last=False)
```

### H5 构建期快照依赖：注册顺序敏感

#### 原代码问题

`graph_builder.py` 在**构建期**把注册表拷贝成一份快照字典（L319-323）：

```python

available_workflows = {}
if self._parent_registry:
    available_workflows.update(self._parent_registry._registry)   # ← 拷贝快照
available_workflows.update(self.workflow_registry)
```

并把该字典经 `create_node(..., workflow_registry=available_workflows)` 交给 `AgentNode`，后者长期持有（`node/agent.py` L26）、在构建期校验存在性（L32-34）、在运行期从**同一份快照**解析（L48）：

```python
# 原代码（节选，node/agent.py）
self.workflow_registry = workflow_registry or {}                       # L26 持快照
if self.agent_config.workflow_id not in self.workflow_registry: raise  # L32-34 构建期校验
sub_workflow = self.workflow_registry.get(self.agent_config.workflow_id)  # L48 运行期仍查快照
```

后果：**先注册 A（引用 B）、后注册 B** 时，A 的快照里没有 B → 构建/运行失败；调换顺序则成功。系统行为依赖注册顺序，报错信息（"not found in registry"）还指向错误方向。

#### 根因分析

把"对注册表的**引用能力**"实现成了"对注册表内容的**值拷贝**"。可变共享资源（注册表）在构建期被拍照后，照片与现实的漂移成为必然。

#### 修复方案

**本期无 AgentNode，但该反模式必须写进《02 · 开发规范》的"架构禁止项"**，约束未来扩展。规范条文：

> **禁止对可变注册表做构建期快照。** 任何节点需要引用其它工作流时，必须在构造期注入一个**惰性解析器（provider）**，在运行期（`execute` 内）才向注册表查询目标；构建期 `validate_config` 只校验引用标识的**格式合法性**（非空、命名规范），不校验存在性；存在性错误在运行期以带上下文的异常（`WorkflowReferenceError: workflow 'B' not registered (referenced by node 'a' in workflow 'A')`）显式抛出。

未来 AgentNode 参考实现（仅示意，本期不落盘）：

```python

```

相应地，`GraphBuilder.build_graph` 不再拼装 `available_workflows` 快照字典；`create_node` 的工厂签名在本期（只有 LLM/HTTP）不需要 `workflow_registry` 参数，保持最小面。

```python
# workflow_engine/logging_conf.py（示意，API 以《01-分阶段开发计划.md · 分阶段开发计划》为准）
import logging, re
from typing import Any

_SECRET_RE = re.compile(
    r"(?i)\b(api[_-]?key|secret|token|password|authorization)\b(\s*[:=]\s*)(\S+)"
)

_MASK = "***REDACTED***"

def redact(data: Any, max_len: int = 500) -> Any:
    """递归脱敏：dict/list/tuple 逐层深入，字符串先截断到 max_len 再做关键字掩码。"""
    if isinstance(data, dict):
        return {k: redact(v, max_len) for k, v in data.items()}
    if isinstance(data, (list, tuple)):
        return type(data)(redact(v, max_len) for v in data)
    if isinstance(data, str):
        clipped = data[:max_len]
        return _SECRET_RE.sub(lambda m: f"{m.group(1)}{m.group(2)}{_MASK}", clipped)
    return data

class RedactFilter(logging.Filter):
    """挂在所有 handler 上：对 msg 与字符串参数做密钥脱敏。"""
    def filter(self, record: logging.LogRecord) -> bool:
        if isinstance(record.msg, str):
            record.msg = redact(record.msg)
        if record.args:
            args = record.args if isinstance(record.args, tuple) else (record.args,)
            record.args = tuple(redact(a) if isinstance(a, str) else a for a in args)
        return True

def setup_logging(level: str = "INFO", *, json_output: bool = False) -> None:
    """结构化 key=value 输出（json_output=True 时 JSON），挂脱敏过滤器；全工程唯一日志入口。"""
    handler = logging.StreamHandler()
    handler.setFormatter(logging.Formatter(
        "%(asctime)s level=%(levelname)s logger=%(name)s %(message)s"
    ))
    handler.addFilter(RedactFilter())
    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(level)
```

### H7 Registry API 不一致：内部映射泄漏

#### 原代码问题

同一个类里并存两个删除 API，语义不一致（`graph_builder.py`）：

```python
# 原代码（节选，graph_builder.py）
def delete_workflow(self, workflow_id):          # L598-605：三张表都删
    if workflow_id in self._registry:
        del self._registry[workflow_id]
        self._definitions.pop(workflow_id, None)
        self._nodes_map.pop(workflow_id, None)
        return True
    return False

def unregister_workflow(self, workflow_id):      # L607-621：只删 _registry
    if workflow_id in self._registry:
        del self._registry[workflow_id]          # _definitions / _nodes_map 泄漏
        return True
    return False
```

调用 `unregister_workflow` 后：`has_workflow` 返回 False，但 `_definitions`（含完整 YAML 定义与 operator_logs）和 `_nodes_map`（含全部节点实例与其执行历史）持续驻留内存——反复注册/注销会无界膨胀，且后续查询接口（`get_workflow_definition` 等）对"已注销"的工作流仍返回数据，状态自相矛盾。此外 `update_workflow`（L565-571）又内联了第三套删除逻辑。

#### 根因分析

- 三张内部映射是**一个聚合的三份投影**，却暴露了"部分删除"的 API，违反"内部状态同增同删"的不变量；
- 同一语义（移除工作流）有两个名字，调用方无从选择。

#### 修复方案

合并为**单一 `delete_workflow`**，在结构守卫锁下对四张表（含 H1 的运行锁表）原子清理；`update_workflow` 复用同一删除路径；**不提供** `unregister_workflow`。落点 `workflow_engine/registry.py`：

```python
# workflow_engine/registry.py（示意）
class WorkflowRegistry:
    def delete_workflow(self, workflow_id: str) -> bool:
        """移除工作流：四张内部映射在同一把锁下同增同删（C6/H7）。"""
        with self._guard:
            existed = workflow_id in self._registry
            self._registry.pop(workflow_id, None)
            self._definitions.pop(workflow_id, None)
            self._nodes_map.pop(workflow_id, None)
            self._run_locks.pop(workflow_id, None)
            if existed:
                logger.info("workflow '%s' deleted", workflow_id)
            return existed

    def update_workflow(self, definition: WorkflowDefinition) -> str:
        self.delete_workflow(definition.workflow_id)      # 复用唯一删除路径
        return self.register_workflow(definition)
```

不变量（写入类的 docstring，作为契约）：**任意时刻，`_registry` / `_definitions` / `_nodes_map` 三者的 key 集合完全相等**（`_run_locks` 按需惰性创建，删除时一并清理）。`load_definitions_from_dir` 批量加载时对每个文件走 `register_workflow`，采用 **fail-fast**：单文件失败即抛带文件路径的 `ValueError`（如 `ValueError(f"load {path} failed: {e}")`），**不**提供"记录并继续 / `strict=True` 二选一"之类待定策略（对应单测 `test_load_definitions_bad_file_fails_fast`）。

- [ ] `ExecutionLog` 序列化结果中不含任何 env 密钥值（有单测证明）。
- [ ] HTTPNode 的 headers/body 不出现在任何 `logger.*` 调用参数中（代码评审确认）。
- [ ] `.env` / `.env.*` 在 `.gitignore` 中；`.env.example` 只列变量名不列值。

### 3.2 日志（H2 / H6 / C3 / C9）

- [ ] 全工程零 `print`（ruff `T201` 通过）；条件路由器仅用 `logger.debug` 记录 `source / matched_target`，**不记录 state**。
- [ ] `setup_logging(level="INFO", *, json_output=False)` 是唯一日志初始化入口；所有 logger 均 `logging.getLogger(__name__)`。
- [ ] `RedactFilter` 挂在 root handler，脱敏单测通过（api_key/token/password/authorization 四类关键字）；`redact(data, max_len=500)` 递归脱敏。
- [ ] 节点运行日志字段白名单：`node_name / node_type / execution_time_ms / status / error`；`ExecutionLog` 的 input/output 经 `_redact_for_log` 截断（上限常量化，如 2000 字符）。
- [ ] 每个 `except` 分支都有 `logger.error(..., exc_info=True)` 或 `logger.warning` 留痕（R6）。

### 3.3 并发（H1 / R3 / R7）

- [ ] `execute_workflow` 对同一 `workflow_id` 持 `threading.RLock` 串行；不同 `workflow_id` 可并行（有测试）。
- [ ] 全链路无"在共享节点实例上就地 mutate 运行态数据"的代码（`grep -n "clear_execution_history" workflow_engine` 仅出现在 `nodes/base.py` 的 K4 兼容定义处，**不被 Registry 调用**）。
- [ ] 并发压测：16 worker × 64 次同 workflow 执行，每次运行日志完整且 `run_id` 互不串扰（integration 标记）。
- [ ] 注册表结构变更（register/update/delete/load）均在 `_guard` 锁内；四张表 key 集合不变量有单测。
- [ ] `RunLogCollector.collect()` 返回排序后的副本，外部不可影响内部；执行结束后 `get_run_collector() is None`（ContextVar 不泄漏）。

### 3.5 错误处理（H2 / R6）
